# Architecture & Technical Design

**Status:** Proposed; validate via thin vertical prototypes before committing to dependencies.

## 1. System boundary

Hypr-Rust is a user-space controller of existing application windows. It does not own the display server, render other apps, or provide a security boundary. Its responsibilities are: observe supported window/display state, compute layouts, request native moves/resizes/focus, and expose control/configuration.

```text
┌────────────────────── UI / app shell ──────────────────────┐
│ tray/menu bar · hotkeys · config/diagnostics · lifecycle    │
└──────────────────────────┬──────────────────────────────────┘
                           │ commands / normalized events
┌──────────────────────────▼──────────────────────────────────┐
│                       Rust shared core                      │
│ domain model · eligibility/rules · layout planner · reducer  │
│ config · action model · event coalescing · observability     │
└──────────────────────────┬──────────────────────────────────┘
                           │ PlatformPort trait
              ┌────────────┴────────────┐
              │                         │
     Windows adapter              macOS adapter
     Win32 window APIs             AX / CoreGraphics / AppKit
     native events/hooks           AX observers / native events
     Windows shell                 menu-bar & permission flow
```

## 2. Workspace/crate layout

```text
Cargo.toml                 # workspace; pin MSRV after dependency spike
crates/
  domain/                   # IDs, geometry, displays, windows, actions, errors
  layout/                   # pure deterministic algorithms and constraints
  config/                   # schema, validation, migration, file IO
  engine/                   # reducer, rules, plan generation, event coalescing
  platform-api/              # traits/capabilities; no OS handles in public types
  platform-windows/          # cfg(windows), Win32 implementation
  platform-macos/            # cfg(target_os = "macos"), AX/AppKit/CoreGraphics
  app/                       # process lifecycle, UI shell, hotkeys, CLI/diagnostics
  test-fixtures/             # synthetic states, golden layouts, fake platform
```

A monorepo workspace keeps platform code and reusable semantics together. Keep OS-specific crates behind target-specific dependencies and compile gates. Prefer stable Rust; use `unsafe` only in tiny audited adapter modules with explicit invariants and safety comments. Exact choice of UI shell, Windows bindings and macOS bindings is an ADR after compiling proof-of-concept examples on actual target OS versions.

## 3. Core domain model

- `WindowKey`: opaque runtime identifier generated by adapter; not a native handle and not persisted.
- `WindowSnapshot`: key, app identity, optional title, frame, state flags, constraints, display key, capability bits, last-observed timestamp.
- `DisplaySnapshot`: runtime key, logical/work-area frame, scale factor, rotation, safe areas/insets where available.
- `Geometry`: logical coordinates represented consistently; no platform integer types in core.
- `LayoutState`: ordered managed windows, tree/stack state, active/focused window, rules, layout parameters, and the OS-reported active workspace identity when available.
- `LayoutPlan`: desired rectangles and safe focus operations with plan revision. Workspace/desktop operations are separate typed platform commands, not geometry or visibility side effects.
- `ApplyReport`: success/unsupported/denied/transient failure per operation, actual observed frame and native error category. Unsupported is a normal capability result, not an exceptional crash.

No native handles, AX references or process pointers cross into `domain`, serialization or logs. Adapter owns handle lifetime and validates that a target still exists before each operation.

## 4. Port interfaces (conceptual)

```rust
trait PlatformPort {
    async fn capabilities(&self) -> PlatformCapabilities;
    async fn enumerate_displays(&self) -> Result<Vec<DisplaySnapshot>, PlatformError>;
    async fn enumerate_windows(&self) -> Result<Vec<WindowSnapshot>, PlatformError>;
    async fn subscribe(&self) -> Result<EventStream, PlatformError>;
    async fn apply(&self, plan: LayoutPlan) -> ApplyReport;
    async fn request_focus(&self, key: WindowKey) -> Result<(), PlatformError>;
}

// Optional adapter contract; implemented/exposed only after platform proof.
trait NativeWorkspacePort {
    async fn capabilities(&self) -> WorkspaceCapabilities;
    async fn active_workspace(&self) -> Result<Option<WorkspaceSnapshot>, PlatformError>;
    async fn switch_to(&self, key: WorkspaceKey) -> Result<(), PlatformError>;
    async fn move_window_to(&self, window: WindowKey, target: WorkspaceKey)
        -> Result<(), PlatformError>;
}
```

`WorkspaceCapabilities` must state per-operation support (detect active/target, switch, move focused window, observe), not a single misleading Boolean. Expose workspace shortcuts only if the complete required set passes on that platform/build; otherwise disable the feature. The final API may use sync/event-loop channels rather than `async`; do not add async solely for fashion. Define cancellation, shutdown and callback lifetime before implementing platform observers. Events are hints; reconcile against a fresh snapshot after missed/coalesced events.

## 5. Event and execution flow

1. Adapter emits normalized event or initial snapshot.
2. Engine updates a single-threaded authoritative state reducer.
3. Eligibility/rules exclude the app's own windows, system/desktop windows, and targets/operations reported unsupported or inaccessible. Ordinary app windows follow user rules; dialogs may be configured where safe.
4. Debouncer coalesces bursts; planner computes a pure geometry `LayoutPlan`.
5. Executor checks generation/revision, applies operations via adapter with limits/rate control.
6. Adapter returns per-operation results and observes resulting actual geometry.
7. Engine reconciles actual state; suppresses events attributable to this plan; retries only safe transient errors with bounded attempts. Denied/unsupported workspace operations leave windows unchanged and are reported; no minimize/hide fallback is allowed.

Native workspace commands are capability-gated and handled by the platform adapter, never emulated with visibility changes. At startup the app follows the currently active OS desktop/space and does not force a switch. Never hold core state locks while calling OS APIs. Avoid unbounded task spawning. Shutdown cancels subscriptions and hotkeys, then leaves windows at their last OS-accepted geometry; do not restore initial geometry.

## 6. Layout engine

Inputs: usable display rectangle, windows in stable order, per-window min/max constraints, layout config and current tree/stack state. Output: complete geometry plan plus diagnostics for unsatisfiable constraints.

Required invariants:

- Rectangles are finite, positive-sized, and within usable area unless policy explicitly allows overflow.
- No overlaps for non-floating windows except layout modes that intentionally stack/monocle.
- Stable ordering and deterministic rounding.
- For BSP, split nodes maintain ratio bounds and prune/rebalance after removals.
- If minimum sizes cannot fit, engine applies documented overflow policy (e.g. clamp + report, or switch affected window to float); never silently produce negative dimensions.
- Coordinate transform (logical points/pixels, scale, origin direction) occurs only at adapter edge.

## 7. Platform adapter responsibilities

### Windows 11

- Enumerate and filter top-level windows; distinguish owned dialogs, cloaked/system windows, minimized/maximized/fullscreen and app-owned UI as robustly as API permits.
- Observe lifecycle, foreground/focus, location and display changes. Prefer event-driven WinEvent hooks; reconcile periodically at a conservative interval only as a fallback.
- Request position/size using supported Win32 APIs (e.g. `SetWindowPos`) and report whether window refused or was immediately repositioned. Respect DPI-awareness, monitor work areas and foreground activation restrictions.
- Treat Windows Virtual Desktop integration as an independent, optional capability. Use only reviewed public/stable APIs; do not assume ordinary Win32 window-positioning APIs can switch desktops or move windows between them. Enable workspace actions only after proof on supported Windows 11 builds.
- Avoid privilege escalation. Admin/elevated target processes may not be controllable from a non-elevated process; explain and fail safely.

### Intel macOS

- Use public Accessibility APIs (`AXUIElement`) for window discovery, attributes, notifications and permitted position/size actions; use public display APIs for monitors/work areas.
- Request Accessibility permission with transparent explanation. Test whether trust is attached to the signed .app identity and how development builds differ.
- Handle per-app AX support variance, missing attributes, stale element references, permission revocation, notifications unavailable and geometry writes denied.
- Treat macOS Spaces integration as an independent, optional capability. Validate required actions using public APIs on Intel macOS Ventura 13+; do not use private WindowServer APIs or assume AX can move/switch Spaces. If requirements are not proven, disable workspace actions on macOS and state why.
- Avoid private WindowServer APIs and do not require disabling SIP. Provide feature capability report if the app cannot control a specific app/window.

## 8. Settings and persistence

- Settings UI is the primary configuration surface. A versioned internal config file may back it; direct TOML editing/import-export is optional and not a v1 requirement.
- Validate candidate settings before applying; invalid changes preserve the last-known-good settings and show actionable diagnostics.
- Write settings atomically (temp + fsync/rename where supported). No arbitrary shell execution in settings/config.
- Store only user preferences/layout settings; do not persist window titles, handles or screen content.
- Auto-tiling remains off until explicit onboarding opt-in; permission grant alone does not enable management.
- At startup follow the OS's current desktop/space; do not force restore/switch. Do not persist native window handles or create app-owned logical workspaces.

## 9. Reliability, security and privacy

- Threat model includes malicious/corrupt config, stale/reused handles, untrusted window titles, app crashes, permission changes, elevated windows and event floods.
- Treat title/app metadata as untrusted text. Escape in UI/logs. Do not construct shell commands from it.
- No cloud service, telemetry or network listener for MVP.
- Avoid storing full window titles in routine logs; diagnostic bundle is explicit user-initiated and redacts sensitive values by default.
- Apply bounded command queue and backpressure. A malformed config must not break emergency quit.
- Code sign/notarize as required by selected macOS distribution; Windows signing plan before public stable distribution.

## 10. Observability

Structured local logs with session ID, platform/API operation, opaque runtime window ID and result category. Default log level INFO; DEBUG must not disclose titles or other sensitive content without explicit opt-in. Diagnostics report permission/capability state, app version, OS version, display scale and last errors.

## 11. Technical spikes required before lock-in

- Mac: Intel Ventura 13+ baseline; AX trust, notification delivery, position/size writes against representative apps; code-signing identity behavior; public-API feasibility for Spaces actions.
- Windows: Windows 11 x64 builds; event hook coverage, mixed-DPI geometry, minimized/fullscreen/dialog filtering, cross-integrity-level behavior, focus restrictions; public-API feasibility for Virtual Desktop actions.
- Workspace spike must list each required operation and evidence. If a platform cannot meet the contract through reviewed public APIs, ship core tiling with workspace controls disabled there—no hidden/minimize fallback.
- Cross-platform: settings/tray/menu-bar shell, hotkey registration, direct packaging/signing/notarization, dependency license review.
